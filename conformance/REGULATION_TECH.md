# Технический регламент допуска к турниру «Метарой 1.0»

Документ дополняет Положение (разд. 7), Постановку задачи (разд. 10, 12, 13) и Приложение А версии 1.0, а также служит инструкцией по самопроверке команд перед финалом.

К турниру допускаются среды и контроллеры без ошибок `FAIL` (`FAIL = 0`, п. 7.8 Положения и п. 1.17 Приложения А). Предупреждения `WARN` не блокируют базовый допуск, но рекомендованы к исправлению (с флагом `--strict` они тоже считаются ошибками).

## 1. Быстрый старт и самопроверка

Командам передаются два файла - `check_tournament.py` (Python 3.9+, только стандартная библиотека) и этот регламент. На Windows вместо `python3` может потребоваться `py`.

Чекер не запускает ваши процессы, он обращается к уже поднятым `env` и `ctrl` по HTTP. Сначала поднимите среду и контроллер по своему README (например, на `http://127.0.0.1:8000` и `http://127.0.0.1:8100`) и убедитесь, что оба отдают `ready`

```bash
curl http://127.0.0.1:8000/v1/environment/health
curl http://127.0.0.1:8100/v1/controller/health
```

Основная команда полной самопроверки

```bash
python3 check_tournament.py selftest \
  --env-url http://127.0.0.1:8000 \
  --ctrl-url http://127.0.0.1:8100 \
  --max-steps 10
```

Она последовательно прогоняет проверку среды (`env`), проверку контроллера (`ctrl`), вашу пару в режиме турнирной нормализации (`pair`), ваш контроллер против встроенной эталонной среды (`pair/ref-env`) и встроенный эталонный контроллер против вашей среды (`pair/ref-ctrl`). Полный прогон занимает 1-2 минуты. Для надежности повторите запуск на нескольких `--seed` (например, `42`, `777`, `123456`).

Можно проверять компоненты отдельно

```bash
python3 check_tournament.py env  --url http://127.0.0.1:8000 --strict
python3 check_tournament.py ctrl --url http://127.0.0.1:8100 --strict
python3 check_tournament.py pair --ctrl-url http://127.0.0.1:8100 --ref-env --normalize
python3 check_tournament.py pair --env-url  http://127.0.0.1:8000 --ref-ctrl --normalize
```

Подсказки по каждому сбою выводятся прямо в консоли в блоке «Что исправить» (с `--json-out report.json` тот же отчет сохраняется в JSON). Встроенные `ref-env` и `ref-ctrl` - это только минимальные тестовые двойники для проверки протокола, а не турнирные решения.

## 2. Уточнения к протоколу v1.0

### 2.1. Координаты
Все координаты `[x, y, z]` передаются в метрах, а высота всегда идет третьей координатой (`z`). Если внутри движка или графики используется ось `Y` вверх, пересчет делается на границе HTTP-интерфейса. В `capabilities.coordinates.axes` следует указывать `["x", "y", "z"]` (третья ось - вертикальная).

### 2.2. Интерфейс контроллера и изоляция эпизодов
Цикл эпизода (`reset -> decide -> step -> close`) ведет турнирный оркестратор. Контроллер обязан принимать два HTTP-запроса (UTF-8, `application/json`)

- `GET /v1/controller/health` по Листингу 8 Приложения А со списком всех 7 операций в `supported_operations`
- `POST /v1/controller/decide` принимает JSON `{"observation": <наблюдение>}` (допускается также сам объект наблюдения) и возвращает решение по Листингу 5 Приложения А

Желательное время ответа на шаг до 1 с, жесткий таймаут оркестратора 15 с. Контроллер, который работает только как клиент и не имеет `POST /v1/controller/decide`, в турнире участвовать не сможет.

Один запущенный процесс контроллера проходит много эпизодов подряд в разных средах. При приходе нового `episode_id` контроллер обязан полностью сбросить состояние прошлого эпизода (карту, историю, убеждения, роли) и не возвращать старые идентификаторы.

### 2.3. Структура решения (Листинг 5)
Решение должно содержать все обязательные поля Листинга 5 - `protocol_version`, `episode_id`, `decision_id`, `request_id`, `time`, `operation`, `previous_configuration`, `selected_configuration`, `candidate_evaluations`, `role_assignments`, `commands`, `constraint_checks`, `explanation`.

- `operation` - только одно из 7 значений (`keep`, `select`, `switch`, `modify`, `compose`, `synthesize`, `safe_stop`)
- `role_assignments` и `commands[].agent_id` - только известные из текущего наблюдения агенты
- `commands[].action` - только из `available_actions` этого агента, для `move` обязателен `{"target": [x, y, z]}` (п. 10.4 ТЗ)
- `constraint_checks[].status` - рекомендуется `passed`, `failed` или `unknown`, при этом среда не должна падать на других строковых статусах в полях аудита
- `explanation` - заполненные `observation_refs`, `reason_codes`, `expected_effects`, `confidence`

### 2.4. Действия и необязательные поля
Контроллер обязан одинаково корректно читать все три варианта `available_actions`

- массив строк `["move", "observe"]`
- массив объектов с ключом `action`, например `[{"action": "move"}]`
- массив объектов с ключом `id`, например `[{"id": "move"}]`

По п. 1.13.1 и п. 1.16 Приложения А и среда, и контроллер обязаны игнорировать неизвестные необязательные поля в теле решения и внутри `commands[].parameters`. Отклонять запрос только из-за лишнего поля нельзя (чекер явно проверяет это через `_optional_hint` и `_ref_optional`).

### 2.5. Наблюдение (Табл. 9), ресурсы и метрики
Среда обязана возвращать все обязательные поля наблюдения (Табл. 9 Приложения А) и вложенные обязательные поля `mission`, `agents`, `infrastructure`, `zones`, `network`, `events`, `observation_quality` (Табл. 3-6, Листинг 6).

Каждый нормированный ресурс должен удовлетворять условию `0 <= minimum <= value <= maximum <= 1` и иметь `unit = "normalized"` (с полем `id` по Листингу 1).

В `observation.metrics` среда должна передавать на каждом шаге

- `mission_completion` - число от `0` до `1`, текущая результативность по п. 12.2 ТЗ (если поля нет, оркестратор вычисляет резервное значение по `targets_rescued / targets_total`, `mission.objectives[].completion` или статусам `targets`)
- `safety_violations` - целое число `>= 0`, накопленное число нарушений безопасности за эпизод

### 2.6. Нормализация п. 1.18 и синтез сценария
В режиме `--normalize` оркестратор удаляет `extensions` и недокументированные поля из основных объектов наблюдения, заменяет все ID агентов, целей, зон и инфраструктуры (включая вложенные ссылки, без затрагивания служебных полей схемы) и перемешивает массивы. Контроллер не должен зависеть от авторских полей, имен или порядка элементов.

Для операции `synthesize` среда обязана принимать минимальную декларацию по Листингу 3 Приложения А без требования авторских полей вроде собственного `graph`.

### 2.7. Журналы и детерминизм
`GET /v1/environment/logs` обязан возвращать валидный JSON или JSON Lines. `GET /v1/controller/logs` не обязателен по базовой версии, но рекомендуется для аудита `M6`.

При одинаковом `seed`, миссии и последовательности решений среда должна выдавать совпадающие публичные наблюдения, события и метрики (п. 1.15 Приложения А).

## 3. Чек-листы проверки

### Среда
| Проверка | Требование |
|---|---|
| `health` и `capabilities` | HTTP 200, `ready`, `protocol_version = "1.0"`, заявлены все 7 операций |
| `reset` и `observation` | Полная схема Табл. 9 + вложенные поля Табл. 3-6 и Листинга 6 |
| Ось `Z` | Высота передается третьей координатой |
| Ресурсы и `metrics` | `0 <= min <= value <= max <= 1`, есть `mission_completion` и `safety_violations` |
| 7 операций и `optional` | Принимаются все 7 операций (включая `synthesize` по Листингу 3), лишние поля в `parameters` игнорируются |
| Ошибки и `safe_stop` | Неизвестный агент дает 4xx или `rejected`, `safe_stop` принимается |
| `logs`, `close`, `seed` | Машиночитаемый журнал, корректное закрытие, совпадение двух прогонов по `seed` |

### Контроллер
| Проверка | Требование |
|---|---|
| `health` и `decide` | HTTP 200, все 7 операций в `health`, рабочий `POST /v1/controller/decide` |
| Листинг 5 и 3 диалекта | Полное решение, чтение строк, `{action}` и `{id}` в `available_actions` |
| Нормализация и `optional` | Работа без `orientation`/`trust`, игнор `_author_specific`, работа с новыми ID |
| Изоляция и ошибки | Сброс состояния на новом `episode_id`, 4xx (не 500) на пустом теле |
| Директивы и журнал | Адекватная реакция на `safe_stop`, желателен `GET /v1/controller/logs` |

### Пара (`pair --normalize`)
- `health`, `reset`, полное наблюдение и валидный Листинг 5 на каждом шаге
- Не менее `--min-steps` (по умолчанию 5) шагов, если эпизод не завершился штатным `success` или легитимной остановкой по директиве
- Рост модельного времени, хотя бы одна команда агенту, наличие `command_results` с принятыми командами и отсутствие необоснованного `safe_stop` на первых шагах

## 4. Частые ошибки при стыковке

1. Нет `POST /v1/controller/decide` (контроллер работает только как клиент) - нужно обернуть шаг контроллера в HTTP-сервер.
2. Среда отклоняет `_optional_hint` или `_ref_optional` - убрать `additionalProperties = false` в параметрах команд.
3. Среда требует свое поле `graph` в `synthesized_scenario` - принимать стандартный Листинг 3.
4. Перепутана ось `Y` и `Z` - переводить координаты в `Z`-вверх на границе HTTP.
5. Среда падает на статусах в `constraint_checks` - не ограничивать информационные поля аудита закрытым списком.
6. Контроллер уходит в `safe_stop` на шаге 1 в чужой среде без директивы - проверить разбор осей, зон и базового профиля.
7. Контроллер завязан на авторские поля (`network.links`, `mission.safe_zones`, `extensions`) - перейти на стандартные `known_links` и `zones`.

## 5. Проведение турнира и подсчет метрик

Оркестратор `run_tournament.py` прогоняет все допущенные пары `(контроллер_i, среда_j)` на общем скрытом наборе `seed` в режиме нормализации.

Автоматическая оценка считается по формуле п. 12.1 ТЗ (`0.30*M1 + 0.20*M2 + 0.10*M3 + 0.10*M4 + 0.10*M5 + 0.10*M6 + 0.10*M7`)

- `M1` - средняя результативность миссии по эпизодам
- `M2` - устойчивость (сохранение результата, отсутствие сбоев протокола и нарушений безопасности при реальной работе)
- `M3` - эффективность ресурсов (остаток энергии, время и доля принятых команд, умноженные на выполненную долю миссии `M1`)
- `M4` - корректность метасценарных решений (валидные операции, принятые команды, отсутствие нарушений и частых переключений)
- `M5` - переносимость, 70% дает работа контроллера в чужих средах и 30% - стабильный прием чужих контроллеров в своей среде
- `M6` - полнота аудиторской цепочки по п. 12.7 ТЗ
- `M7` - качество среды (результат проверок допуска и стабильность с чужими контроллерами)

Если среда или контроллер требуют отдельное железо (например, Windows и видеокарту), команда сдает готовую рабочую сборку с инструкцией запуска или дает сетевой доступ к поднятому стенду на время турнира.
