## Порядок реализации и проверки

1. Собрать строгий публичный профиль и явно выбранный режим объявленной
   совместимости. Проверить исходные JSON отдельно от видов для планировщика.
   Проверить схемы ссылок без сетевого разрешения. Сохранить аудит всех
   преобразований с episode/request ID.
2. Выделить связывание намерения с wire-действием, доступностью, единицами и
   схемой аргументов. Поддержать нестандартные ID только при декларации
   семантики. Расширить кандидаты сценариев по опубликованным условиям,
   параметрам, ролям и переходам.
3. Провести калибровку Net65 по публичной геометрии и по уже подтверждённым
   естественным действиям. Подтверждённые повторные осмотры считать по
   свежей квитанции результата. При недостаточных измерениях оставить
   доступные действия штатного публичного планировщика.
4. Самостоятельные среда и контроллер используют стандартную библиотеку
   и собственную проверку А §1.17–1.18. В матрице отдельные режимы
   геометрии, событий и связи, переименований, совместимости и физики.
5. Испытать шесть направлений на трёх новых seed, затем неизменённые
   архивы Lab, Portable, Atlas и Metaroi v9. Ошибки воспроизвести
   диагностическими входами. Отчёт разделяет поддержку протокола,
   физический успех, реальную работу Net65 и внешнее межкомандное
   подтверждение. Если публичных доказательств цели нет, результат
   остаётся unverified.

### Исправления границы ресурсов и планарного стенда

По Приложению А, §1.5, стр. 9–10, обязательны нормированные границы ресурса;
равенство ключа объекта и отдельного id — форма собственного профиля
(`stage-1-interaction.md`, раздел Resources), а не явно заданное условие
для чужих инфраструктурных объектов. Проверка числовых границ и обязательного
id сохраняется, для инфраструктуры исключена навязанная эквивалентность.
Для ресурсов агентов сохраняется текущий контракт семантических ключей
планировщика; неоднозначные обозначения требуют дальнейшей отдельной проверки.
В PlanarServer исправлен хэш исходного тела запроса для объявленной
дедупликации. Планарная среда публикует допустимый диапазон координат и
ранее существующий default radius=15 для observe. Ошибка схемы команды
содержит индекс, действие, путь и отсутствующие параметры. Эти изменения
общие, без подстановки ID партнёров; нативная среда ими не изменена.

### Устойчивость чужих схем и HTTP-корреляции

Неизвестный тип JSON Schema, битый локальный указатель, циклическая
ссылка или недопустимое регулярное выражение переводятся в ProtocolError,
а не в необработанное исключение библиотеки. Объявленные схемы параметров
команд и сценариев проходят проверку metaschema; до 64 небольших схем
(не более 64 KiB ключа) кэшируются по содержимому. Проверка обязательных
структур и отсутствие сетевого разрешения ссылок сохранены. HTTP 3xx
не считается подтверждением команды/решения; переадресации не следуют.
Неудачное обновление capabilities не устанавливает новые гарантии retry.


### Дополнительная проверка причинной корреляции

Явно чужой episode_id в ACK/событии не переименовывается в эпизод
HTTP-оболочки. Повторное использование request_id для разных decision_id
инвалидирует связанные подтверждённые цели и публичные переходы, включая
ранее накопленные записи. Для legacy applied/accepted проверяются все
присутствующие ID, индекс и отсутствие терминального отказа. Некорректные
необязательные записи журнала не могут сами создать доказательство.
Отрицательные тесты сохраняют отдельный положительный legacy fixture.
